## 1. Обзор проекта

Discord-бот для маркетплейса «Клондайк Шёпота»: фиксация сделок, тикеты с формами, OCR
распознавание скриншотов, ранги/рефералы с авто-выдачей ролей, управление ценами/товарами,
аналитика продаж — всё поверх Google Таблицы как базы данных (через `gspread`).

Дополнительно в директории присутствует независимый **selfbot** (`selfbot/main.py`) —
рекламный self-bot (автопостинг + автоответы в ЛС), не имеющий отношения к основному боту.

Стек: Python 3.12, `discord.py 2.4`, `gspread`, `pydantic-settings`, `easyocr` (OCR),
`simpleeval` (безопасный калькулятор выражений).

## 2. Архитектура

В проекте одновременно существуют **две полные, независимые реализации одного и того же бота**:

### 2.1 `bot/` — слоистый пакет (актуальная, эксплуатируемая версия)

```
bot/
├── __main__.py        # точка входа (console-script "bot", запускается через `python -m bot`)
├── cogs/               # discord.py Cogs — слой представления/команд
│   ├── admin_cmds.py   # /logs, /give_price, /price_list, /new_price
│   ├── analytics.py    # /day, /week, /month
│   ├── items.py        # /setprice, /setboost, /item_add, /del_item, /sync_prices
│   ├── profile.py      # /profile, /refer, /referrals
│   ├── roles.py        # /set_rank, /set_referral (+ автовыдача ролей)
│   ├── tickets.py       # тикет-визард, OCR по скриншотам, /tag (1343 строки!)
│   └── transactions.py # /add + record_transaction() — общая точка фиксации сделки
├── config/
│   ├── constants.py    # индексы колонок Google Sheets, ID каналов/ролей, пороги
│   └── settings.py     # pydantic-settings (.env)
├── models/              # dataclass'ы User, Transaction (Item не хватает — см. §6)
├── repositories/
│   └── sheets_repository.py  # единственная точка доступа к Google Sheets API
├── services/
│   ├── sheets_service.py     # User/Transaction поверх repo
│   ├── user_service.py       # бизнес-правила профиля/реферала
│   ├── referral_service.py   # уровни рангов/рефералов, бонусы (дублирует role_service!)
│   ├── role_service.py       # назначение Discord-ролей + свои копии порогов/бонусов
│   ├── audit_logger.py       # embed-логирование команд в audit-канал
│   └── ocr_service.py        # easyocr + сопоставление с prices.json
└── utils/
    ├── calculator.py   # safe_calc() — безопасный eval арифметики
    ├── embeds.py       # построение embed'ов профиля/рефералов/ошибок
    └── logger.py       # настройка логирования
```

Слои: **Cog (представление) → Service (бизнес-логика) → Repository (Google Sheets)**.
Зависимости внедряются через атрибуты `bot.repo`, `bot.sheets_service`, `bot.user_service`,
`bot.referral_service`, `bot.audit_logger`, которые создаются в `bot/__main__.py:main()`
и раздаются когам в `setup(bot)`.

Подтверждено записью в `selfbot/scripts/start_bot.sh`: `venv/bin/python -m bot` —
именно этот пакет реально запускается в продакшене.

### 2.2 `bot.py` — монолитный файл в корне (1743 строки, параллельная реализация)

Содержит **всё то же самое** — Google Sheets клиент, OCR, калькулятор, embeds, роли,
аудит, аналитику и все 19 слэш-команд — но одним файлом, без слоёв, с собственным
`main()` и собственным `on_ready`/`on_message`/`setup_hook`.

- Не является частью устанавливаемого пакета: отсутствует в
  `discord_trade_bot.egg-info/SOURCES.txt`, нигде не импортируется (`grep` не нашёл
  ни одного `import bot.py` / `from bot.py` за пределами самого файла).
- При этом **активно редактируется** — последний коммит `9d157f0` от 2026-07-29 23:40,
  то есть *позже*, чем последний коммит в `bot/__main__.py` (`0bca8c1`, 03:23 того же дня).
  Это означает, что кто-то продолжает вносить правки в обе реализации параллельно,
  рискуя логическим расхождением («в одном месте починили — в другом нет»).

**Это центральная архитектурная проблема проекта** — см. §5.1 и §7.1.

### 2.3 `selfbot/` — независимый скрипт (реклама/автоответчик)

`selfbot/main.py` — self-bot на `discord.py-self`, не связан с основным ботом кодом,
но эксплуатационно относится к тому же Discord-серверу. Полностью в `.gitignore`
(последняя строка `.gitignore`: `selfbot/`), поэтому не версионируется вообще.

### 2.4 Хранилище данных

- **Google Sheets** (через `gspread`) — единственный источник правды: сделки, пользователи,
  база товаров, все формулы (Coins/XP/ранг вычисляются формулами в самой таблице,
  бот их не пересчитывает).
- **Локальные JSON-файлы** как побочные кэши/состояние:
  - `prices.json` — кэш цен для OCR-сверки (синхронизируется из Sheets).
  - `referrals.json` — счётчик рефералов по Discord ID (используется только в
    `role_service.py`, но нигде не находит применения из когов — см. §6, мёртвый код).
  - `published_requests.json` — метаданные опубликованных карточек заявок (для кнопки
    «Изменить заявку»), пишется/читается в `tickets.py`.
  - `deal_reports/<channel_id>.json` — журнал форм/OCR по каждому тикет-каналу.

## 4. Зависимости между модулями (граф)

```
bot/__main__.py
  ├── bot/config/settings.py            (Settings)
  ├── bot/repositories/sheets_repository.py
  │     └── bot/config/constants.py
  ├── bot/services/sheets_service.py
  │     ├── bot/models/user.py, transaction.py
  │     └── bot/repositories/sheets_repository.py
  ├── bot/services/user_service.py
  │     ├── bot/models/user.py
  │     └── bot/services/sheets_service.py
  ├── bot/services/referral_service.py
  │     └── bot/repositories/sheets_repository.py
  └── bot/services/audit_logger.py       (только discord.py)

Коги (загружаются setup_hook, зависят от bot.<attr>, а не от прямого DI):
  bot/cogs/profile.py       → bot.user_service, bot.referral_service, bot.audit_logger (utils/embeds)
  bot/cogs/transactions.py  → bot.sheets_service (utils/calculator, embeds)
  bot/cogs/tickets.py       → создаёт свой OcrService(), берёт bot.audit_logger,
                              напрямую обращается к interaction.client.repo (!),
                              вызывает interaction.client.get_cog("TransactionsCog") (!)
  bot/cogs/roles.py         → создаёт свой RoleService() (не берёт из bot.*)
  bot/cogs/items.py         → напрямую берёт bot.repo (минуя services/)
  bot/cogs/admin_cmds.py    → напрямую берёт bot.repo (минуя services/)
  bot/cogs/analytics.py     → напрямую берёт bot.repo (минуя services/)

bot.py (монолит) — не зависит от bot/* вообще, дублирует все модули внутри одного файла.
```

Замечания по графу:

1. **Непоследовательный DI.** `ProfileCog` и `TransactionsCog` получают зависимости через
   сервисный слой (`bot.user_service`, `bot.sheets_service`), а `ItemsCog`,
   `AdminCmdsCog`, `AnalyticsCog` обращаются к `bot.repo` **напрямую**, минуя
   `SheetsService`. Это два разных архитектурных стиля в одном пакете — часть
   функциональности (цены/товары/логи/аналитика) вообще не проходит через service-слой,
   хотя он для этого и создавался.
2. **Скрытая связь через `interaction.client`.** `bot/cogs/tickets.py` достаёт ког
   транзакций через `interaction.client.get_cog("TransactionsCog")` (строковая связь,
   не проверяемая на этапе импорта) и репозиторий через `interaction.client.repo`
   (обходя `bot.sheets_service`/`user_service`, которыми пользуется тот же `TransactionsCog`
   в других местах). Итог: тикеты и транзакции связаны неявно, через рантайм-атрибуты
   `bot`, а не через явные конструкторы — это форма **высокой связности через глобальное
   состояние** (см. §9).
3. **Дублирование role-конфигурации.** `RANK_ROLES`/`REFERRAL_ROLES`/пороги/бонусы
   определены (с одинаковыми ID/значениями) сразу в: `bot/config/constants.py`,
   `bot/services/role_service.py`, `bot/services/referral_service.py`,
   `bot/cogs/transactions.py`, `bot/cogs/tickets.py` — **5 независимых копий одних
   и тех же констант** (плюс шестая — в `bot.py`). См. §8.2.
4. **Циклических импортов между модулями `bot/` не обнаружено** — граф ациклический
   (Cogs → Services → Repositories → Config, без обратных импортов). Единственная форма
   «цикличности» — рантайм-связь Cog↔Cog через `interaction.client.get_cog(...)`
   и Cog↔Bot через динамические атрибуты, что не ловится статическим анализом импортов,
   но по сути создаёт скрытую двустороннюю зависимость `tickets.py ⇄ transactions.py`.

## 5. Потенциальные проблемы и технический долг

### 5.1 Два независимых, расходящихся entry point'а (критично)

`bot.py` (монолит) и `bot/` (пакет) реализуют один и тот же функционал по-разному:

- Аналитика: `bot.py::_build_analytics_embed` трактует `is_buy`/`is_sell` **иначе**,
  чем `bot/cogs/analytics.py::_build_analytics_embed` (в пакетной версии есть подробный
  комментарий, разъясняющий семантику «продал боту / купил у бота»; в `bot.py` этого
  разъяснения нет и агрегация суммарно иная: `total_buy`/`total_sell` считаются
  напрямую от `tx["type"]`, без адаптации к «прибыли бота»).
- `/week` в `bot.py` принимает `год`+`неделя` (номер ISO-недели), а в пакете —
  `диапазон` строкой `ДД.ММ.ГГГГ - ДД.ММ.ГГГГ`. Разный UX для одной команды.
- `bot.py` использует **cell-based** запись в Google Sheets (`update_cell` по одной
  ячейке в цикле в `_sync_prices_to_sheets`), тогда как
  `bot/repositories/sheets_repository.py::sync_prices_to_sheets` намеренно переписан
  на батч (`update_cells`) — в коде даже есть комментарий, поясняющий, что
  поячеечная запись раньше проглатывала ошибки квоты API. **Этот баг-фикс не попал
  в `bot.py`** — то есть один из двух файлов содержит уже устранённую в другом
  проблему.
- Если кто-то по ошибке (или из привычки) запустит `python bot.py` вместо
  `python -m bot` — получится другой бот с другим набором мелких расхождений
  в логике, что почти невозможно обнаружить без построчного диффа.

**Рекомендация:** удалить `bot.py` (либо явно пометить как архив/референс вне
рабочего дерева) — его существование создаёт риск регрессий и путаницы при любой
правке, вносимой «в одном месте, но не в другом».

### 5.2 God-файл `bot/cogs/tickets.py` (1343 строки)

Один файл содержит: FormDataStore, JSON-хранилище заявок (save/load/find/delete),
построение карточки-эмбеда, `DeliveryMethodSelect/View`, 3 модальных окна
(`BaseOrderModal`, `BoostOrderModal`, `SaleModal`), `BoostSelectionView`,
`QuantityEditModal`, `BoostQuantityView` (с постраничной пагинацией и динамическими
callback'ами), `ScreenshotPromptView`, `EditRequestModal/View`, `ConfirmModal`,
персистентную `TicketFormView`, и сам `TicketCog` с обработкой OCR и слушателями
`on_guild_channel_create`/`on_thread_create`/`on_message`. См. §10 (большие функции/классы).

### 5.3 Хрупкий парсинг данных из Google Sheets

`SheetsRepository._parse_float/_parse_int` молча возвращают `0.0`/`0` при ошибке
парсинга (`except ValueError: return 0.0`), без логирования. Если в таблице
руками ввели мусор в числовую колонку — бот тихо посчитает это нулём, без
какого-либо предупреждения администратору. То же самое дублируется (с разной
надёжностью) в `bot.py::_gs_parse_float`, `admin_cmds.py::_parse_amount_logs`,
`analytics.py::_parse_float` — три с половиной независимые копии одной функции
(см. §8.1 DRY).

### 5.4 Поиск по Google Sheets — O(n) построчный перебор без кэша

`SheetsRepository._find_cell_icase`/`_find_all_icase` реализованы через
`col_values()` + линейный перебор в Python (обёртка `gspread.find`/`findall` не
используется намеренно ради case-insensitive поиска). Каждый вызов команды
(`/profile`, `/add`, `/refer`, `/setprice`...) тянет полный столбец из Google Sheets
API синхронно (обёрнуто в `asyncio.to_thread`, так что event loop не блокируется,
но задержка на пользователя остаётся). При росте таблицы (сотни/тысячи строк) и
частых командах это упирается в Google Sheets API rate limit (100 запросов/100 сек
на пользователя по умолчанию) — сейчас частично смягчено ретраями (`_retry`,
экспоненциальный backoff, `MAX_RETRIES=3`), но не кэшированием.

### 5.5 Общая изменяемая память как «база данных» тикетов

`FormDataStore` (`bot/cogs/tickets.py`) хранит состояние заполнения формы в
`dict[int, dict]` **в памяти процесса**, без TTL и без персистентности. При
перезапуске бота — все незавершённые формы теряются без уведомления
пользователя. Аналогично `_role_referrals`-подобные кэши (в `bot.py`) хранятся
только в оперативной памяти между операциями записи в файл.

### 5.6 Отсутствие тестов

В проекте нет ни одного тест-файла (`test_*.py`, `pytest`, `tests/`) — ни для
`safe_calc` (парсинг произвольных пользовательских математических выражений —
как раз то место, где тесты нужнее всего), ни для парсинга колонок Sheets,
ни для расчёта рангов/уровней. Вся валидация — ручная, по логам после деплоя
(что подтверждается объёмными `bot_error.log`/`bot_output.log` в корне репозитория).

### 5.7 Рассинхронизация зависимостей `pyproject.toml` ↔ `requirements.txt`

`pyproject.toml` не содержит `simpleeval`, `Pillow`, `numpy`, `opencv-python-headless`,
хотя `bot/utils/calculator.py` и OCR-сервис их используют (`simpleeval` — прямая
зависимость `safe_calc`, `Pillow`/`numpy` — прямая зависимость `ocr_service.py`).
Установка через `pip install -e .` (как рекомендовано в README) не подтянет эти
пакеты — бот упадёт на первом вызове `/add` или OCR. Только `requirements.txt`
содержит полный набор.

### 5.8 Логи в корне репозитория, не покрытые `.gitignore`

`bot_error.log` (28 КБ) и `bot_output.log` (34 КБ) лежат в корне рабочего дерева.
`.gitignore` их не исключает явно (только `*.json`, `.env`, `venv/`, `__pycache__/`,
`*.egg-info/`) — риск случайного `git add .` и утечки внутренних деталей инфраструктуры
(traceback'и, ID каналов, временные сетевые сбои) в историю репозитория.

### 5.9 Общий `except: pass` / `except Exception: pass` антипаттерн

Повсеместно (особенно в `bot.py`, но и в `bot/cogs/*`) аудит-логирование обёрнуто
в `try/except: pass` — само по себе разумно (не хотим ронять команду из-за сбоя
логирования), но паттерн используется и там, где он **маскирует настоящие ошибки**:
например, `bot/repositories/sheets_repository.py::_ensure_jrow` целиком в
`try/except Exception: pass` — если Google Sheets API вернёт ошибку при копировании
формул, она проглатывается молча, и пользователь получит "успешную" сделку без
скопированных формул K–U (нарушение целостности данных без каких-либо следов в логах).

## 6. Неиспользуемые файлы / мёртвый код

| Объект | Статус |
|---|---|
| `bot.py` (весь файл, 1743 строки) | Не импортируется нигде, не входит в устанавливаемый пакет (`SOURCES.txt` его не содержит). Полный дубль `bot/`. Формально «работоспособен» (можно запустить как отдельный скрипт), но не используется production-скриптами запуска (`selfbot/scripts/start_bot.sh` запускает `python -m bot`). |

## 7. Нарушения принципов проектирования

### 7.1 DRY — наиболее выраженная проблема проекта

Самое масштабное нарушение — уже описанный полный дубль `bot.py` ↔ `bot/*`
(§2.2, §5.1). Ниже — дублирование **внутри** самого пакета `bot/`:

1. **Ролевые константы и пороги** продублированы в 4 местах пакета (плюс `bot.py`):
   - `bot/config/constants.py`: `RANK_THRESHOLDS`, `RANK_ROLES`, `REFERRAL_THRESHOLDS`, `REFERRAL_ROLES`
   - `bot/services/role_service.py`: те же 4 словаря, с теми же ID, повторены дословно
   - `bot/services/referral_service.py`: `THRESHOLDS`, `REF_ROLE_NAMES`, `RANK_THRESHOLDS`,
     `RANK_NAMES`, `RANK_BONUSES`, `LEVEL_NAMES`, `LEVEL_BONUSES` — параллельный набор
     той же самой бизнес-логики, но с другой формой хранения (списки вместо dict)
   - `bot/cogs/transactions.py`: собственные `RANK_ROLES`/`REFERRAL_ROLES` с эмодзи в
     ключах (`"🔹 Standard"` вместо `"Standard"`) — **третий, несовместимый формат
     ключей** для тех же ID ролей
   - `bot/cogs/tickets.py`: `RANK_ROLES_MAP`/`REFERRAL_ROLES_MAP` — **пятая копия**
     тех же ID (используется только для `_role_mention`, не задействуется, т.к. в
     tickets.py авто-роль назначается не напрямую, а через `record_transaction`)

   Если ID роли на сервере Discord изменится, его нужно поправить в 5 (пакет)
   + 1 (bot.py) = 6 местах одновременно. Любая пропущенная копия — тихий баг.

2. **`_fmt`/форматирование чисел** — реализовано отдельно и слегка по-разному в:
   `bot/services/ocr_service.py::_fmt`, `bot/utils/embeds.py::_fmt` (с разделителем
   тысяч пробелом — отличается от версии в `ocr_service.py`!), `bot/cogs/admin_cmds.py::_fmt`,
   `bot/cogs/analytics.py::_fmt`, `bot/cogs/transactions.py::_amount_str`, плюс
   `bot.py::_fmt`. Шесть слегка разных реализаций одной и той же идеи "красиво
   показать число" — при этом `bot/utils/embeds.py::_fmt` единственная добавляет
   разделители тысяч, остальные — нет, то есть **числа в разных embed'ах бота
   форматируются заведомо по-разному** (`/logs` — "1500000", `/profile` — "1 500 000").

3. **Парсинг чисел из ячеек Sheets** (`_parse_float`/`_parse_amount_logs`) — 4 копии
   (см. §5.3).

4. **`resolve_emoji`** реализован дважды: `bot/utils/embeds.py::resolve_emoji` (публичная,
   переиспользуемая) и приватная `_EMOJI_RE`/логика внутри `bot.py::_resolve_emoji` —
   идентичная логика, независимая копия.

5. **`PriceListView`** — определена дважды с идентичной логикой пагинации:
   `bot/cogs/admin_cmds.py::PriceListView` и `bot.py::PriceListView` (плюс третья
   концептуальная копия паттерна пагинации в `bot/cogs/admin_cmds.py::LogsView`
   и `bot/cogs/tickets.py::BoostQuantityView` — четыре независимые реализации
   "постраничного View с ◀/▶ кнопками", ни одна не переиспользует общий базовый класс).

6. **`safe_calc`** — идентичная реализация присутствует в `bot/utils/calculator.py`
   и (дословно скопирована) в `bot.py::safe_calc`.

### 7.2 SOLID

- **SRP (Single Responsibility):**
  - `bot/cogs/tickets.py` нарушает SRP массивно: один модуль отвечает за хранение
    состояния форм, персистентность заявок в JSON, построение embed'ов, весь UI-визард
    (5+ View/Modal классов), OCR-обработку сообщений, слушатели создания каналов/тредов
    и slash-команду `/tag`. Это не один Cog с одной ответственностью, а фактически
    отдельный под-модуль приложения, живущий в одном файле.
  - `bot/repositories/sheets_repository.py` смешивает низкоуровневый доступ к API
    (`_find_cell_icase`, retry-обёртки) с бизнес-специфичной логикой синхронизации
    трёх конкретных внешних листов по хардкод-именам (`sync_prices_to_sheets` знает
    про «Мейн скуп», «Скуп бустов», «БУСТЫ» — это доменные правила, которым место
    в сервисном слое, а не в репозитории).
  - `RoleService.__init__` совмещает две ответственности: (а) расчёт целевой роли
    по порогам и (б) персистентность JSON-счётчика рефералов (`_load_referrals`,
    `_save_referrals`) — при этом (б), как выяснено в §6, мёртвый код.

- **OCP (Open/Closed):** добавление нового листа синхронизации цен или новой
  ранговой роли требует правки констант сразу в нескольких файлах (см. DRY выше) —
  система не закрыта для расширения без модификации существующего кода в N местах.

- **DIP (Dependency Inversion):** сервисы и коги зависят не от абстракций, а от
  конкретного класса `SheetsRepository` напрямую (нет интерфейса/протокола
  `Repository`). Это затрудняет unit-тестирование (нет тестов — см. §5.6) и
  подмену хранилища (например, для локальной разработки без реального Google
  Sheets аккаунта). Кроме того часть когов получает репозиторий напрямую
  (`bot.repo`), а часть — через сервисный слой (`bot.sheets_service`), то есть
  сама точка внедрения зависимости несогласованна (см. §4 п.1).

- **LSP:** явных нарушений подстановки не обнаружено (класс-иерархий с
  переопределением поведения, ломающим контракт базового класса, нет — проект
  почти не использует наследование за пределами discord.py Views/Modals).

- **ISP:** не применимо в чистом виде (Python, отсутствуют явные интерфейсы),
  но косвенно нарушается тем, что коги (`tickets.py`) обращаются к
  `interaction.client.repo` напрямую, то есть зависят от **всего** интерфейса
  бота (`commands.Bot` + произвольные динамические атрибуты), а не от узкого
  протокола, который им реально нужен.

### 7.3 KISS

- `bot/cogs/tickets.py::BoostQuantityView` реализует ручную пагинацию с
  динамически создаваемыми `discord.ui.Button` (через `lambda i, gi=...: ...`)
  вместо декларативных `@discord.ui.button` — усложняет чтение и отладку
  (ошибка в замыкании `lambda` — частый источник багов "все кнопки ведут на
  последний элемент", здесь избегнута через `gi=global_idx` в аргументе
  по умолчанию, но сама конструкция всё равно менее очевидна, чем декларативный
  стиль, используемый в остальном коде).
- `safe_calc()` — самописный "safe eval" через строковую регекс-очистку
  (`re.sub(r'[^\d.,+*/\skк-]', '', expression)`) поверх `simpleeval` с фолбэком
  на `float(cleaned)`, обёрнутый в try/except с проглатыванием исключений —
  усложнённое решение простой задачи "распарсить арифметическое выражение
  с суффиксом k/к"; сама простая конкатенация двух парсеров (regex-предобработка
  + eval-библиотека) увеличивает площадь атаки и число неочевидных крайних
  случаев (например, `"1k+2к"` даст `"1*1000+2*1000"`, а `"1-к"` после очистки
  превратится в мусор, который тихо упадёт в `float(cleaned)` и кинет ValueError
  без вменяемого сообщения пользователю).
- Дублирующиеся, слегка отличающиеся друг от друга форматтеры чисел (§7.1 п.2)
  — простая задача форматирования решена 6 разными способами вместо одной
  общей утилиты.

## 9. Места с высокой связностью (high coupling)

1. **`interaction.client.<attr>`-паттерн.** Практически все коги (`items.py`,
   `admin_cmds.py`, `analytics.py`, `tickets.py`) достают зависимости не через
   конструктор (`__init__`), а через `interaction.client.repo` /
   `interaction.client.audit_logger` внутри тела обработчика команды. Это
   связывает каждый обработчик с конкретной структурой объекта `bot` (Service
   Locator антипаттерн вместо Dependency Injection) — сложно тестировать
   изолированно, легко сломать при рефакторинге `bot/__main__.py`.
2. **`tickets.py::ConfirmModal.on_submit`** явно достаёт другой ког по строковому
   имени: `interaction.client.get_cog("TransactionsCog")` — связь между двумя
   когами не выражена типами/импортом, а рантайм-строкой; переименование класса
   `TransactionsCog` тихо сломает подтверждение сделок в тикетах без ошибки на
   этапе загрузки экстеншенов.
3. **Общие захардкоженные ID Discord-сущностей** (каналы, роли, категории)
   разбросаны по `bot/config/constants.py`, `bot/cogs/tickets.py`,
   `bot/cogs/transactions.py`, `bot/services/role_service.py` и `bot.py` —
   любой из этих модулей знает "магические числа" сервера напрямую, вместо
   единой точки правды.
4. **`bot/cogs/tickets.py`** связан практически со всем: `SheetsRepository`
   (через `interaction.client.repo`), `TransactionsCog` (через `get_cog`),
   собственным `OcrService`, файловой системой (`published_requests.json`,
   `deal_reports/`) — самый высокосвязанный модуль проекта, что напрямую
   коррелирует с его размером (§5.2) и нарушением SRP (§7.2).

### 10.4 Мёртвый/бессмысленный код (отдельно от §6)

`bot/services/referral_service.py::ReferralService.get_target_referral_name`:

```python
@staticmethod
def get_target_referral_name(count: int) -> Optional[str]:
    for i, threshold in enumerate(THRESHOLDS):
        if count >= threshold and i < len(REF_ROLE_NAMES):
            pass                      # <-- ничего не делает, мёртвый цикл
    target = None
    for i, threshold in enumerate(THRESHOLDS):
        if count >= threshold:
            target = REF_ROLE_NAMES[i]
    return target
```
Первый цикл — очевидный остаток черновика, не выполняет никакой полезной работы
и должен быть удалён при следующей правке файла (не проблема поведения, но
явный шум/технический долг).

## 11. Циклические зависимости

**На уровне статических импортов Python** — циклов не обнаружено. Граф импортов
`bot/` строго однонаправленный: `cogs → services → repositories → config/models`,
без обратных `import`.

**На уровне рантайм-связей** (не видна статическому анализатору, но по сути —
двусторонняя зависимость):

```
bot/cogs/tickets.py  --get_cog("TransactionsCog")-->  bot/cogs/transactions.py
bot/cogs/transactions.py  <--вызывается из--  ConfirmModal.on_submit (tickets.py)
```

Формально не цикл импортов (transactions.py не импортирует tickets.py), но
логически — двусторонняя функциональная зависимость через рантайм-реестр когов
`bot.cogs`, что несёт те же риски, что и обычный цикл: изменение сигнатуры
`TransactionsCog.record_transaction` без синхронной правки `tickets.py` завершится
ошибкой только в момент вызова (после подтверждения сделки в тикете), а не на
старте бота или статическим анализом.
