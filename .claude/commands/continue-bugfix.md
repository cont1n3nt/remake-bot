Продолжи работу над проектом по плану исправления багов.

ПЕРЕД НАЧАЛОМ ИЗУЧИ: plan.md, bugfix.md, bugfix_progress.md, progress.md.

1. Найди в bugfix_progress.md первый этап со статусом "not started"/"in progress".
2. Изучи актуальный код этого модуля заново (не полагайся на память из bugfix.md).
3. Исправляй баги по порядку severity (critical → high → medium → low), 
   используя /debugging-and-error-recovery для сложных/непонятных случаев 
   (reproduce → localize → reduce → fix → guard).
4. Для security-багов — прогони фикс через агента security-auditor, чтобы 
   убедиться, что закрыта причина, а не симптом.
5. Если у бага стоит "нужен regression-тест: да" — напиши тест по скиллу 
   /test-driven-development (red-green-refactor: сначала тест воспроизводит 
   баг, потом фикс, потом тест зелёный).
6. После правок всего этапа — обязательный прогон /code-review-and-quality 
   по изменённым файлам. Учитывай change sizing (~100 строк на ревью) — 
   если правок вышло больше, дели на подкоммиты.
7. Если код после фиксов стал сложнее, чем нужно — примени 
   /code-simplification (Chesterton's Fence: не выпиливай то, назначение 
   чего не понял, сначала разберись).
8. Закоммить изменения по /git-workflow-and-versioning — атомарные коммиты 
   по одному багу/группе связанных багов, осмысленные сообщения.
9. Обнови bugfix_progress.md: [x] по багам, статус этапа, "review passed: да/нет",
   заметки — что поменял, что показал review, на что смотреть дальше.
10. Новые баги, найденные по пути — добавляй в bugfix.md и в текущий/следующий 
    этап bugfix_progress.md, не исправляй сразу, если не блокируют текущий этап.

ВАЖНО:
- Только один этап за раз, не забегай вперёд.
- Этап считается завершённым ТОЛЬКО когда code-review-and-quality пройден 
  и bugfix_progress.md обновлён.
- Как только этап готов — ОСТАНОВИСЬ, дай отчёт (что исправлено, что показал 
  review, что добавилось нового, что дальше). Не начинай следующий этап 
  без явной команды.
