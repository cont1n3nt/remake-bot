## 1. Метод

Зафиксировано только то, что можно проверить статически или по существующим
артефактам (компиляция, импорт модулей, статический анализ, логи прошлых
запусков), **без** реального запуска `python -m bot`/`bot.run()`. Причина:
в `.env` заполнены все обязательные переменные (`DISCORD_TOKEN`,
`GOOGLE_SHEETS_URL`, `GUILD_ID` и др. — см. §2.3), поэтому реальный запуск
подключил бы боевого Discord-бота к реальному серверу и вызвал бы
`bot.tree.sync(guild=...)` (живая мутация списка слэш-команд гильдии) — это
действие с видимым эффектом на общей системе, которое не выполнялось без
отдельного подтверждения. Вместо этого состояние «запускается ли бот»
подтверждено импорт-проверкой всех модулей и историческими логами реальных
прошлых запусков (`bot_output.log`, `bot_error.log`, оставшиеся в рабочем
дереве).

## 2. Запускается ли проект

### 2.1 Синтаксис и импортируемость — OK

- `py_compile` по всем `.py`-файлам `bot/` и по `bot.py` — ошибок нет.
- Импорт по отдельности всех 23 модулей пакета `bot/` (`config`, `models`,
  `repositories`, `services`, `utils`, все 7 когов, `bot.__main__`) —
  все импортируются без исключений на уровне модуля.
- `bot.py` (монолит) также импортируется без ошибок при загрузке напрямую по
  пути (`importlib.util.spec_from_file_location`). Обычный `import bot`
  резолвится в пакет `bot/` (`bot/__init__.py`), а не в `bot.py` — то есть
  монолит в принципе недостижим через стандартный импорт под именем `bot`,
  что подтверждает вывод `AUDIT.md §2.2`: он не является частью пакета.
- И `bot/__main__.py::main()`, и `bot.py::main()` вызываются только под
  `if __name__ == "__main__":` — сам факт импорта модуля не запускает бота
  и не открывает сетевое соединение.

### 2.2 Команды запуска

- **По факту в проде** (`selfbot/scripts/start_bot.sh`):
  ```
  cd /root/bot
  screen -dmS discord_bot bash -c "venv/bin/python -m bot"
  ```
  Запускается пакет `bot/` через `python -m bot`, без предварительного
  `pip install`, из корня репозитория (работает, т.к. `bot/` — обычный пакет
  в текущей директории, попадающей в `sys.path`).
- **По README.md**:
  ```
  cp .env.example .env
  pip install -e .
  bot
  ```
  т.е. предполагается editable-install и запуск через console-script `bot`.
- **Расхождение (новая находка, не было в AUDIT.md):** в текущем `venv/`
  проекта пакет `discord-trade-bot` **не установлен** —
  `pip show discord-trade-bot` возвращает `Package(s) not found`, и в
  `venv/Scripts/` отсутствует исполняемый файл `bot`/`bot.exe`. При этом
  `discord_trade_bot.egg-info/` присутствует в корне репозитория (устаревшие
  метаданные — см. `AUDIT.md §6`). То есть инструкция запуска из README
  (`pip install -e .` → `bot`) в текущем окружении **не сработает** «из
  коробки» — команда `bot` не существует, пока кто-то заново не выполнит
  `pip install -e .`. Реально работает только `python -m bot` из корня
  репозитория (как в prod-скрипте).

### 5.2 Ошибки из логов прошлых боевых/тестовых запусков

`bot_error.log`/`bot_output.log` в рабочем дереве (не в `.gitignore` —
см. `AUDIT.md §5.8`) содержат записи о реальных инцидентах за 2026-07-27:

1. **`discord.app_commands.errors.CommandNotFound: Application command
   'set_referral' not found`** (дважды, 18:04:55 и 18:06:43) — slash-команда
   `/set_referral` была вызвана пользователем/клиентом Discord, но не
   найдена в дереве команд бота на тот момент (рассинхронизация
   зарегистрированных команд с тем, что видел клиент — типично после
   переименования команды без `tree.sync()` на клиенте или во время
   деплоя новой версии).
2. **`discord.errors.HTTPException: 400 Bad Request (error code: 40060):
   Interaction has already been acknowledged`** в команде `profile`
   (18:29:14) — по traceback'у это происходит внутри **`bot.py:861`**
   (`await interaction.response.defer(ephemeral=True)`), то есть лог
   зафиксировал реальный прогон именно монолита `bot.py`, а не пакета
   `bot/` — прямое подтверждение того, что кто-то параллельно запускал оба
   entry point'а локально (см. `AUDIT.md §5.1`). Сама ошибка — повторный
   `defer()`/`response` на уже подтверждённое взаимодействие (гонка/двойной
   вызов обработчика).
3. **Серия `discord.client: Attempting a reconnect in N.NNs`** (19:09:37 →
   19:10:41, экспоненциально растущие паузы 1.76s → 3.48s → 3.05s → 13.51s
   → 19.65s → 36.86s) с причиной
   `aiohttp.client_exceptions.ClientConnectorDNSError: Cannot connect to
   host gateway-us-east1-b.discord.gg ... getaddrinfo failed` и
   `OSError(22, ...)` при подключении к `discord.com` — сетевая проблема на
   машине разработки в момент записи лога (DNS/сеть недоступны), не баг в
   коде бота; после восстановления сети бот успешно переподключился
   (`Shard ID None has connected to Gateway`).
4. **`asyncio: Task exception was never retrieved`** (18:08:37) — то же
   семейство сетевых обрывов (`ClientConnectorError`), исключение из
   таска `CommandTree-invoker` не было обработано/дождано — сам факт «never
   retrieved» указывает, что где-то в цепочке обработки interaction
   отсутствует `try/except` вокруг сетевого вызова к Discord API.
5. **`discord.ext.commands.bot: Privileged message content intent is
   missing, commands may not work as expected`** (17:56:57) — предупреждение
   при старте о том, что Message Content Intent не включён в Discord
   Developer Portal для приложения, при этом код (`bot/__main__.py:34`)
   явно запрашивает `intents.message_content = True`. Практическое
   следствие: любая логика, читающая текст/вложения обычных сообщений (в
   частности, OCR-обработка скриншотов в `bot/cogs/tickets.py` по событию
   `on_message`), может не получать содержимое сообщений, пока intent не
   включён на портале разработчика.
6. **Мусорная кодировка кириллицы в `bot_output.log`.** Файл определяется
   как `ISO-8859 text` (не UTF-8); строки вида `[WARNING] bot: ...` с
   русским текстом читаются как «мусор» (`�...`) при чтении в UTF-8. Это
   означает, что логгер (`bot/utils/logger.py`) пишет файл не в UTF-8 (или
   наследует кодировку консоли Windows по умолчанию, обычно cp1251), из-за
   чего часть диагностических сообщений на русском языке фактически
   нечитаема при последующем анализе логов другими инструментами.
