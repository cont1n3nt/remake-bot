### ⚡ CLUSTER-1 — Гонка при подтверждении сделки: возможна двойная запись строки в Тикеты
**Найдено независимо 4 агентами: APP-1 (application), TICK-1 (tickets), SEC-3 (security), TEST-1 (test-coverage)**

- Файлы:
  - `src/stalbot/application/services/transactions.py:86-154` (`register`, `_replay_if_seen`, `_find_free_row`)
  - `src/stalbot/infrastructure/cache/repositories/idempotency.py:17-42` (`get`/`record`, `INSERT OR IGNORE`)
  - `src/stalbot/infrastructure/sheets/client.py:105-173` (`batch_update`/`write_verified` — лок держится только вокруг самого `batch_update`, read-back верификация уже вне лока)
  - `src/stalbot/presentation/cogs/tickets/cog.py:571-634` (`_confirm_precheck`, `_on_confirm_button`, `_on_amount_submitted`)
- Описание: `_replay_if_seen()` читает `IdempotencyRepository.get(key)` без блокировки; ключ записывается только **после** завершения записи в Sheets (`idempotency.record()`). Два конкурентных вызова с одним и тем же ключом (двойной клик «✅ Подтвердить», два админа одновременно, гонка `_find_free_row` при двух разных `/add`) оба проходят replay-проверку до того, как первый успел записать — оба вычисляют одну и ту же «свободную» строку (`_find_free_row`, тоже без лока) и оба пишут. Второй `write_verified` затирает данные первого; read-back первого видит расхождение → компенсация «очистить A-E,H» стирает **уже корректно записанные данные второго**. Дополнительно: `is_first_transaction` (referrer → колонка `H`) может сработать `True` в обоих конкурентных вызовах для нового игрока → двойной счёт реферала через `СЧЁТЕСЛИ($H:$H)` в колонке `P`.
- Severity: **critical** (реальная гонка в единственном источнике правды — торговом реестре; деньги/игровая валюта могут быть потеряны или задвоены)
- Кто выявил: `agent-skills:code-reviewer` (APP слой, TICK слой) через `debugging-and-error-recovery` (root-cause трассировка гонки) + `agent-skills:security-auditor` (SEC-3, тот же баг с фокусом на «real-money ledger») + `agent-skills:test-engineer` (TEST-1: подтвердил, что ни один тест не проверяет настоящую конкурентность — только последовательные вызовы)
- Предлагаемый фикс: держать **один и тот же** `asyncio.Lock` (по каналу тикета / по `idempotency_key`) на весь путь find-row → write → verify → record, а не только вокруг сетевого вызова. Простейший вариант — сериализовать весь `TransactionService.register()` одним грубым локом (пропускная способность admin-команд низкая, это приемлемо).
- Regression-тест нужен: **да** — `asyncio.gather(register(req), register(req))` с одинаковым `idempotency_key` против fake `SheetsClient`; assert `write_verified` вызван ровно один раз и обе строки не сталкиваются. Отдельный тест на конкурентную первую-сделку двух новых игроков с одним рефералом → `H` пишется один раз.
- Зависимости: фикс в `TransactionService`/`SheetsClient` автоматически закрывает и TICK-1 (UI-сторона гонки в `cog.py`), но там дополнительно нужен `_confirm_precheck`, перечитывающий статус **прямо перед** записью, а не только при показе модалки.

### INFRA1-1 — `ensure_writable()` пропускает проверку защищённых колонок при «перевёрнутом» диапазоне (fail-open)
- Файл: `src/stalbot/infrastructure/sheets/protection.py:43-51`
- Описание: `for index in range(start, end + 1)` — если каким-то образом `end &lt; start` (например, диапазон вида `"DataBase!G3:F3"`), `range()` в Python пуст, и **ни одна колонка не проверяется** — запись в формульную колонку (F/G/J-P/R/S) уходит в сеть без единственного заявленного «fail loudly and locally» барьера.
- Severity: **critical** — нарушает абсолютный инвариант проекта («бот никогда не пишет формулу») в единственной точке его принудительного соблюдения.
- Кто выявил: `agent-skills:code-reviewer` (sheets/cache) через five-axis review (edge case на границах колонок, именно то, что просили проверить)
- Предлагаемый фикс: `lo, hi = sorted((start, end)); range(lo, hi + 1)`, либо явный `ValueError` на некорректный/перевёрнутый диапазон вместо молчаливого принятия.
- Regression-тест нужен: **да** — `ensure_writable("DataBase!G3:F3")` должен поднять `ProtectedRangeWriteError`. Сейчас не поднимет.
- Зависимости: нет.

### DOM-1 — `evaluate_amount` тихо портит точные денежные суммы через обязательный float-роундтрип
- Файл: `src/stalbot/domain/money.py:207-253`
- Описание: числовые токены переформатируются в текст и повторно парсятся через `ast.parse` — но в грамматике Python нет литерала fixed-point, поэтому любой токен с точкой становится `float` (IEEE-754) до того, как `_eval_node` конвертирует его обратно в `Decimal(str(...))`. Круглый путь точен только пока значение помещается в ~15-17 значащих цифр float64.
  ```python
  evaluate_amount("999999999999999.99")  # -> Decimal('1000000000000000.0')  НЕВЕРНО, скачок на порядок
  ```
  Достижимо на бытовых суммах в диапазоне квадриллионов — легко получить через множитель `ккк` (×10⁹) на скромной базе. Прямое нарушение задокументированного инварианта «money must ALWAYS be Decimal, never float» — как раз для функции, которая обслуживает `/add`, подтверждение тикета, `/setprice`, `/setboost`, `/new_price`, итоги заказа бустов.
- Severity: **critical** — тихая порча денежных данных, достижимый ввод, прямое нарушение задокументированного инварианта; проскочило мимо 113+ существующих тестов и hypothesis-свойства (они не гоняют высокоточные дробные литералы именно через AST-путь).
- Кто выявил: `agent-skills:code-reviewer` (domain) через five-axis correctness + целевой поиск «floating point creeping in»
- Предлагаемый фикс: не пропускать десятичные литералы через нативную грамматику `ast.parse`. Заменять каждый распознанный денежный токен плейсхолдер-идентификатором (`__m0__`), привязанным к предварительно распарсенному `Decimal` в отдельной таблице; `ast.Name` резолвится через lookup, а не через `ast.Constant.value`.
- Regression-тест нужен: **да** — `evaluate_amount("123456789012345.6789") == Decimal("123456789012345.6789")` (сейчас падает), плюс кейс `.99`, скачивающий на порядок.
- Зависимости: независим от DOM-3 (другая причина/порог), но оба трогают один и тот же блок кода — логично чинить в одном заходе.

### APP-2 — `int()`-усечение при записи в Sheets расходится с `Decimal`, закэшированным/показанным пользователю
- Файлы: `application/services/transactions.py:105-116,167`; `pricing.py:89-96,144-150,281-287`; `catalog.py:86-98,168-177`
- Описание: запись в Sheets везде идёт через `int(request.amount)` (усечение к нулю, не округление), а закэшированный/возвращённый объект использует **неусечённый** `Decimal`. В `TransactionService.register()` это означает, что пользователь видит в эфемерном подтверждении одно число, а в реестре оказывается другое (усечённое). В `PricingService`/`CatalogService` расхождение вообще не самокорректируется последующим синком (в отличие от `transactions.py`, где синк хотя бы частично лечит кэш) — рассинхрон кэша и таблицы держится до случайного полного ресинка. Также игнорируется собственная конвенция округления `domain/money.py::format_amount` (`ROUND_HALF_UP`).
- Severity: **critical** (transactions.py — видимое пользователю расхождение реестра/подтверждения), **high** (pricing/catalog — тихий, несамокорректирующийся дрейф кэша)
- Кто выявил: `agent-skills:code-reviewer` (application) через five-axis correctness, сверка 5 мест записи с одинаковым паттерном
- Предлагаемый фикс: единая функция `round_for_storage(value: Decimal) -> Decimal` в `domain/money.py` с той же конвенцией `ROUND_HALF_UP`, что и `format_amount`; каждое место записи использует ровно это округлённое значение и для payload в Sheets, и для объекта, который кэшируется/возвращается — никогда два независимо выведенных значения одного поля.
- Regression-тест нужен: **да** — вызов каждого из 5 мест с дробным `Decimal` (напр. `Decimal("150.5")`), assert записанное в Sheets и закэшированное/возвращённое значение совпадают.
- Зависимости: все 5 мест могут чиниться одним общим хелпером за один проход.

### INFRA1-2 — Ложное несовпадение при read-back верификации может стереть корректно записанную строку
- Файл: `src/stalbot/infrastructure/sheets/client.py:159-173` (`write_verified`/`_matches`)
- Описание: сравнение `result.get(ref, []) == list(values)` — строгое сравнение вложенных списков. Google Sheets API документированно обрезает висячие пустые ячейки/строки при чтении (не дополняет обратно). Строка, оканчивающаяся пустой строкой (частый случай — колонка `H`/«Пришёл от» пуста при сделке без реферала), почти наверняка вернётся короче отправленной → **ложное несовпадение** → компенсация стирает только что корректно записанную строку и поднимает `SheetsWriteConflictError` пользователю на успешно записанные данные.
- Severity: **critical/high** — ложное срабатывание сети безопасности может уничтожить корректно записанные данные реестра; тот же класс бага («API-квирк ломает сопоставление»), что автор уже дважды ловил раньше в этом же клиенте.
- Кто выявил: `agent-skills:code-reviewer` (sheets/cache) через `debugging-and-error-recovery` (паттерн совпадает с задокументированным историческим багом `batch_get`)
- Предлагаемый фикс: сравнивать по ячейкам с right-padding более короткой (read-back) строки/грида до формы записанной, трактуя отсутствующую висячую ячейку как равную явно записанной `""`.
- Regression-тест нужен: **да** — `write_verified` со строкой, оканчивающейся `""`, где мокнутый `values_batch_get` возвращает её без висячей пустой ячейки — не должен ни стирать, ни поднимать исключение. Существующие тесты `test_write_verified_*` используют только непустые скалярные ячейки.
- Зависимости: нет напрямую, но общий корень с задокументированным историческим квирком `batch_get`.

**DOM-2 / ⚡ дублирует SEC-2** — `parse_deadline`: необработанный `OverflowError` от простого текстового поля Discord
- Файл: `src/stalbot/domain/clock.py:124-125,180-191` (`_RELATIVE_HOURS_RE`/`_RELATIVE_MINUTES_RE`, `_parse_relative_hours`/`_parse_relative_minutes`)
- Описание: `int(match.group(1))` не ограничен по числу цифр, передаётся в `timedelta(hours=...)`/`timedelta(minutes=...)`. Достаточно большое число переполняет внутреннее C-int представление `datetime` → `OverflowError`, не пойманный нигде выше по стеку. Поле заполняется **обычным игроком** (автором тикета) в модалке заказа бустов, помещается в лимит `max_length=50` (`"через 999999999999999999999999999999 часов"` — 42 символа). Модалка не проходит через общий `on_app_command_error` (это `discord.ui.Modal.on_error`, у которого нет обработчика) — падение тихое, без ответа пользователю, без trace_id в логах.
- Severity: **high** — необработанный краш от непривилегированного пользовательского ввода, нарушает собственный контракт иерархии исключений проекта.
- Кто выявил: `agent-skills:code-reviewer` (domain, DOM-2) независимо от `agent-skills:security-auditor` (SEC-2, тот же баг с фокусом на непривилегированный доступ и отсутствие error-хендлинга в модалках)
- Предлагаемый фикс: ограничить число цифр в регулярке (`(\d{1,6})`) или поймать `OverflowError`/`ValueError` вокруг `timedelta(...)` и переподнять как `DeadlineParseError`.
- Regression-тест нужен: **да** — `parse_deadline("через 999999999999999999999999999999 часов", now=...)` должен поднять `DeadlineParseError`.
- Зависимости: связан с SEC-4 (общий пробел — у Modal вообще нет `on_error`).

## Security — дополнительные находки (не вошедшие в кластеры выше)

**SEC-1** — `evaluate_amount` принимает нативный синтаксис scientific notation Python (`"1e400"`), даёт `Decimal('Infinity')`/`OverflowError`
- Файл: `domain/money.py:178-223`
- Описание: `_NUMBER_SPAN_RE` не распознаёт экспоненциальную нотацию, поэтому `ast.parse` видит её как обычный float-литерал — переполняется в `inf` без `SyntaxError`; whitelist AST пропускает `inf` (это легальный `float`). Только для админских команд (`/add`, `/setprice`, `/setboost`, подтверждение суммы) — не эксплуатируется рядовым игроком, но небрежный ввод админом роняет команду необработанным `OverflowError` вместо понятной ошибки валидации.
- Severity: medium.
- Кто выявил: `agent-skills:security-auditor`.
- Фикс: явно отклонять нефинитные результаты (`if not result.is_finite(): raise AmountParseError(...)`).
- Regression-тест: да — `"1e400"`, `"1e309"`, `"1e400 - 1e400"`, `"-1e400"` должны давать `AmountParseError`.
- Зависимости: тот же файл/функция, что DOM-1/DOM-3 — логично чинить всё evaluate_amount в одном заходе.

**SEC-4** — Системный пробел: ни один Modal в проекте не переопределяет `on_error`, поэтому будущие исключения в любой модалке падают тихо
- Обобщение корневой причины DOM-2/SEC-2 на весь `presentation/cogs/tickets/modals.py`.
- Severity: low (обобщение, не новый инцидент).
- Фикс: общий базовый класс/миксин `on_error`, маршрутизирующий через ту же `_resolve_message`/embed-конвенцию, что и `errors.py`.
- Regression-тест: не обязателен отдельно (закрывается тестом DOM-2/SEC-2); рекомендован один smoke-тест на видимость ошибки.

**SEC-5** — Нет per-user cooldown на «тяжёлых» админских командах (`/sync_prices`, `/new_price`)
- Severity: low — требует уже привилегированного (админ) аккаунта для эксплуатации; последствие — деградация задержки, не потеря данных.
- Фикс: `app_commands.checks.cooldown` как defense-in-depth, не срочно.

**SEC-6** — systemd unit можно защитить сильнее (доп. sandboxing-директивы)
- Присутствующее уже корректно (`NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `ReadWritePaths`) — подтверждено, не просто заявлено.
- Отсутствует: `ProtectKernelModules`, `ProtectKernelTunables`, `ProtectControlGroups`, `RestrictSUIDSGID`, `RestrictNamespaces`, `LockPersonality`, `SystemCallFilter=@system-service`, `CapabilityBoundingSet=`.
- Severity: info — не блокирует, нет известного пути эксплуатации.

### Security — чисто, без замечаний (явно проверено)
Секреты (токен/ключ сервис-аккаунта нигде в git-истории, `.gitignore` корректен), SQL-инъекции (везде параметризовано), `eval`/`exec` в `evaluate_amount` (AST-whitelist корректно отклоняет `__import__`, атрибуты, вызовы, подписки, comprehensions, lambda, walrus), авторизация (`admin_only()` — оба слоя защиты на каждой админ-команде без исключений), CSRF/CORS (N/A — нет HTTP-сервера), Dockerfile non-root, docker-compose read-only mount креденшлов.

## Найдено при исправлении Этапа 0 (2026-08-05)

**INFRA1-11** — `TransactionService.register()` теперь сериализован одним общим локом
(фикс CLUSTER-1), но ни один Sheets-вызов внутри защищённого пути (`write_verified`,
`_await_formulas`'s `read_until`, `_extend_formulas`) не имеет таймаута — `retry_with_backoff`
реагирует только на пойманный `APIError`, зависшее TCP-соединение никогда его не бросит.
- Файлы: `application/services/transactions.py` (`register`/`_register_locked`),
  `infrastructure/sheets/client.py` (`_ensure_open`/`batch_get`/`batch_update` — все идут

  (`retry_with_backoff`).
- Описание: до фикса CLUSTER-1 зависший сетевой вызов блокировал только вызвавший его
  запрос. После фикса он блокирует ЛОК на весь процесс — один завис­ший `/add` или
  подтверждение тикета останавливает вообще все админ-действия с деньгами до рестарта
  бота. Рост blast radius — прямое следствие сделанного в Этапе 0 фикса, подтверждено
  `security-auditor` (severity: medium) при ревью CLUSTER-1.
- Severity: **medium** (self-inflicted DoS на core money-path, не эксплуатируется
  извне, но триггерится обычным сетевым сбоем).
- Предлагаемый фикс: `asyncio.wait_for(...)` вокруг Sheets-вызовов внутри залоченного
  пути и/или таймаут на HTTP-сессии `gspread`-клиента.
- Regression-тест нужен: да — зависший `write_verified` не должен блокировать процесс
  бесконечно.
- Зависимости: делит корень с INFRA1-3 (тот же пробел — `retry_with_backoff` не ловит
  сетевые сбои вне `APIError`); логично чинить в одном заходе с Этапом 3.
